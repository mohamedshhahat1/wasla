# Wasla — Authentication and Authorization

**Reviewed:** 2026-08-23 · **Tree:** Phase 15 + auth hardening + ADR-037/038/039
**Companion documents:** [SECURITY.md](SECURITY.md), [../SECURITY_AUDIT.md](../SECURITY_AUDIT.md), [../MULTI_TENANT_AUDIT.md](../MULTI_TENANT_AUDIT.md)

This is the authorization model as **enforced**, not as intended. The matrix in
§4 is generated by walking FastAPI's dependency graph, so it describes what the
code actually resolves — which is how two of the defects in §6 were found.

---

## 1. Principals

Six, and the distinction that matters most is that the last two are a property
of the **user row**, while the middle three are a property of a **membership**.

| Principal | What it means | Where it lives |
|---|---|---|
| **Anonymous** | No credential presented | — |
| **User** | Authenticated, no workspace selected | `users` |
| **MEMBER** | Holds a membership in the active workspace | `memberships.role` |
| **TENANT_ADMIN** | Administers one workspace | `memberships.role` |
| **TENANT_OWNER** | Owns one workspace; the only role that can touch money | `memberships.role` |
| **PLATFORM_STAFF** | `PLATFORM_OWNER` or `PLATFORM_ADMIN` | `users.platform_role` |

**Owning a workspace confers nothing across the platform, and holding a platform
role confers no membership.** The two guards read different sources
(`require_tenant_roles` reads `workspace.role`; `require_platform_roles` reads
`current_user.user.platform_role`) and neither consults the other. Platform
routes resolve no workspace at all, which is why they appear as "no" in the
workspace-scoped column rather than as some implicit workspace.

## 2. How a request is authorized

Four gates. Each would have to fail independently.

1. **The tenant comes from the signed token, never from request input.** No
   route accepts a `tenant_id` in a path, query or body. There is no field to
   forge.
2. **The claim is re-verified per request, and only an *active* membership
   counts.** `get_active_workspace` re-reads the membership through a
   tenant-scoped repository — filtered to `status = active` (ADR-038) — and
   re-reads the tenant's status. A token naming a workspace the user never
   joined is refused; a suspension or a revocation takes effect on the next
   request rather than at token expiry. This is the single enforcement point
   for membership revocation, which is why §4's matrix is generated rather than
   written: "every workspace route resolves this dependency" is a claim about
   the dependency graph, and it is checked by walking it.
3. **The tenant predicate is applied in one place.** `TenantScopedRepository`
   takes the tenant at construction and applies it in `_select()`;
   `_tenant_filter()` is an `@abstractmethod`, so a repository that forgets it
   cannot be instantiated. A miss raises `TenantIsolationError`, which answers
   **404 with a generic message** — never 403, because distinguishing "not
   yours" from "does not exist" confirms the id names a real row.
4. **Services are constructed with a tenant and never accept one.** Every
   provider builds its service from `workspace.tenant.id`, so a route has no way
   to express the wrong workspace even by mistake.

## 3. Tokens

| Property | Value |
|---|---|
| Algorithm | Explicit allowlist — `algorithms=[settings.jwt_algorithm]`, default `HS256`. The setting itself is validated to the HMAC family at startup, so `none` and the asymmetric families cannot be configured (§6.6) |
| Issuer | Validated (`iss` = `wasla`) |
| Required claims | `iss`, `sub`, `typ`, `jti`, `iat`, `exp` |
| Type confusion | `typ` is compared against the expected kind; an access token is refused where a refresh token belongs |
| Access lifetime | 900s, carries `tid` |
| Refresh lifetime | 14 days, carries **no** `tid` — so switching workspace never needs a new refresh token |
| Refresh rotation | The presented token is spent with a single atomic `SET NX` in Redis (ADR-039) |
| Refresh reuse | A second presentation loses the `SET NX` race, which raises `users.token_version` — invalidating every token the account holds — and writes a `refresh_token_reused` audit entry |
| Revocation | `ver` claim compared against `users.token_version` on **both** token kinds (ADR-036) |
| Audience | Not used, and no `aud` claim is issued — nothing to validate |

There is exactly one `jwt.decode` in the codebase and it verifies. No code path
decodes without verification, so algorithm confusion has no entry point.

**The signing key is required in every environment except `test`.** See §6.1 —
this was previously enforced only when `ENVIRONMENT` was literally `production`.

### The twelve unauthenticated routes

Nine under `/api/v1`, plus the three health endpoints. Every one is deliberate,
and each carries a different justification.

The count was wrong before this revision: the two password-reset routes shipped
with ADR-042 and were never listed here. Email verification adds none - **both
of its routes require a session**, which is what removes the enumeration
surface rather than mitigating it (ADR-043).

| Route | Why it is open | What bounds it |
|---|---|---|
| `POST /auth/register` | Self-service signup | Client-address limit |
| `POST /auth/login` | Credentials are what it establishes | Client-address **and per-account** limit |
| `POST /auth/refresh` | The refresh token is the credential | Client-address limit; a replay tears the account's session estate down (ADR-039) |
| `POST /auth/logout` | Revoking a token you hold needs no second credential | Nothing — see §7 |
| `POST /auth/password-reset/request` | The caller cannot sign in; that is what it is for | Client-address limit; one constant 202 whatever the address is |
| `POST /auth/password-reset/confirm` | The emailed token in the body is the authorization | Client-address limit; one constant refusal for every dead token |
| `POST /invitations/accept` | The invitee may have no account yet; the token in the body is the authorization | Client-address limit |
| `GET /webhooks/whatsapp` | Meta's subscription challenge | Verify token, compared in constant time |
| `POST /webhooks/whatsapp` | Meta cannot hold a credential of ours | HMAC-SHA256 signature; **never** rate-limited (ADR-032); 1 MB body cap |
| `GET /health`, `/health/live`, `/health/ready` | A load balancer has no credential | Report status and a version, never a connection string or a dependency error |

The webhook is the only unauthenticated **write** path, and its signature check
is the whole of its authorization.

## 5. Rate limiting

Four policies, and the identity each counts by matters more than the numbers.

| Policy | Counts by | Default | Why that identity |
|---|---|---|---|
| `auth` | Client address | 10/min | The caller has no identity yet |
| `auth:account` | **Account named** (SHA-256 of the lower-cased address) | 5/min | Address limits count the attacker's machines; this one does not care how the traffic is distributed |
| `workspace` | Workspace | 300/min | Protects shared resources; per-user would let a large customer exhaust the platform while every individual stayed polite |
| `campaign` | Workspace | 30/min | Expensive to serve, rare to make |

**Client identity.** A forwarding header is believed **only when the connection
came from a listed proxy** (`TRUSTED_PROXY_IPS`, empty by default). From a
trusted peer, `X-Real-IP` wins; failing that, `X-Forwarded-For` is walked from
the right to the last entry that is not itself a trusted proxy. From anyone else
both headers are ignored and the socket address is used.

The limiter **fails open** on a Redis error, deliberately (ADR-032): a cache
outage should not become a total outage. That is a real residual risk for the
authentication policy specifically, and it is recorded as W-14.

## 6. Defects found by this review, and what was done

### 6.1 The signing key was only checked in production — fixed

`jwt_secret` defaulted to the placeholder `change-me`, and the hardening
validator returned early unless `environment` was exactly `"production"`. Two
consequences, both easy to miss:

- `staging` is a first-class tier here and is internet-reachable — Meta must
  deliver webhooks to it — and it skipped the check entirely.
- `environment` itself defaults to `local`, so a container started **without**
  `ENVIRONMENT` set skipped the check too. The guard protecting the key was
  opt-in through a field that defaults to the unprotected side.

A key that ships in the repository is not a secret, it is a checksum: anyone
holding it can mint a token for any `sub`, including one carrying a platform
role, and `get_current_user` trusts a valid signature completely.

**Fixed** in `app/core/config.py`: the rule now applies in every environment
except `test`. The production block additionally requires `DOCS_ENABLED=false`
and a `META_APP_SECRET`. `.env.example` ships an empty `JWT_SECRET`, and CI
generates one per run for the container smoke test rather than using a committed
value.

### 6.2 Authentication rate limiting was bypassable — fixed

`client_identity` read the **first** entry of `X-Forwarded-For`. That value is
attacker-supplied in both topologies: behind no proxy trivially, and behind the
shipped nginx because `$proxy_add_x_forwarded_for` **appends** the real peer to
whatever arrived, leaving the first entry as whatever the caller sent. Rotating
the header put every attempt in its own bucket, so the limit never engaged — and
it was the only anti-automation control in front of `/auth/login`.

**Fixed** as described in §5, and a **per-account limit** was added, because no
address-based limit can stop distributed credential stuffing. It is applied
before the account is looked up, so it costs an attacker their budget whether or
not the address exists — which stops the limit becoming an enumeration oracle of
its own.

### 6.3 `POST /invitations/accept` required authentication — fixed

`invitations.router` was in `WORKSPACE_ROUTERS` and included with
`dependencies=[Depends(workspace_rate_limit)]`. That guard's signature begins
`workspace: ActiveWorkspaceDep`, so FastAPI resolved the entire authentication
chain for **every** route on the router — including the one whose docstring says
"Unauthenticated on purpose: the invited person may have no account yet."
Onboarding answered 401 to exactly the people it exists for.

The existing test passed because it requested a fixture that had already
overridden `get_active_workspace`.

**Fixed**: the router moved to a `MIXED_ROUTERS` group with no router-level
dependency, and each route declares its own limit — the workspace limit on the
three authenticated ones, a client-address limit on `/accept`.

### 6.4 Tool grants were not enforced at execution — fixed

A workspace grants an agent named tools. Only granted tools were **described** to
the model, but `ToolRegistry.run` resolves a name against the whole deployment
registry — so any tool the deployment implements would execute if the model named
it. A model naming a tool it was never offered is not hypothetical: the names are
ordinary English, and the conversation contains text written by a stranger whose
message the model reads as instructions.

The exposure was concrete. An agent granted nothing but a handoff could be talked
into calling `search_knowledge`, which reads the workspace's private documents
and returns them into a reply the customer receives.

**Fixed** in `AgentOrchestrator._run`: the granted set is checked before dispatch,
and an ungranted call returns a refusal the model can adapt to rather than
executing. A grant is an authorization decision, so it is enforced where the
authority is used, not only where the menu is written.

### 6.5 The review's own tooling read the wrong tree — fixed

Worth recording because it invalidates conclusions rather than code. The script
that walks the dependency graph was run as a file from a scratch directory, so
`sys.path[0]` was that directory and `import app` resolved to the **installed**
package in the main checkout rather than to the worktree under review. It
reported 98 operations and a clean matrix while the tree actually contained 106.

Every route added in this change — the members router, the number release, and
the ADR-036 account routes — was silently absent from the matrix, and the walk
that was supposed to prove "every workspace route resolves the workspace
dependency" was proving it about somebody else's code.

**Fixed** by running the generator with `PYTHONPATH` pinned to the tree under
review, and cross-checked against `app.openapi()` — 106 operations walked, 106
in the schema, nothing missing in either direction. The lesson generalises: a
review tool that reads the wrong tree fails silently and in the reassuring
direction.

### 6.6 `JWT_ALGORITHM` accepted anything — fixed

`jwt_algorithm: str = "HS256"` was a free string with no validation, and it is
the value passed to PyJWT's `algorithms=` allowlist — which is otherwise the
entire defence against algorithm confusion.

Two configurations were reachable. `none` would have put the null algorithm in
the allowlist; PyJWT happens to refuse a non-empty key for it today, which means
the protection was somebody else's implementation detail rather than ours. And
naming `RS256` would have had the application verify with `jwt_secret` as a
public key — the classic confusion, where anyone who learns the "public" key can
sign. There is no key-pair configuration in this application, so an asymmetric
algorithm cannot be set up correctly here, only incorrectly.

**Fixed** in `app/core/config.py`: `jwt_algorithm` is validated against
`{HS256, HS384, HS512}` and normalised to upper case, so a misconfiguration is a
container that will not start rather than an authentication system that quietly
stops meaning anything.

### 6.7 A WhatsApp number could be claimed without proof — fixed

The finding recorded as W-02 / M-01, and the only one in these reviews that
crossed a tenant boundary through ordinary use. `phone_number_id` was unique
platform-wide and nothing checked whether the workspace claiming one controlled
it. The identifier is not secret — it is in every webhook payload — so a
workspace that knew a competitor's number could claim it and become the tenant
every inbound message for it resolved to.

**Fixed** by ADR-037: the connect request now carries a Meta access token, the
claim is verified against the Graph API for that exact number before anything is
written, and the business account is taken from Meta's answer rather than the
request. The platform credential is deliberately not a route to this — it can
read every number the platform is connected to, so it would prove nothing about
the workspace making the claim.

### 6.8 A workspace could not remove a member — fixed

`memberships` had no status column and there was no members router, so access to
a workspace could be granted and never withdrawn. Recorded as W-03a.

**Fixed** by ADR-038: `memberships.status`, enforced in `get_active_workspace`,
which every workspace-scoped route already resolves — so a revocation takes
effect on the next request without touching the person's account, their other
workspaces or their tokens.

### 6.9 Reuse of a refresh token was detected and not acted on — fixed

Recorded as W-10. The presented token was refused; the thief's chain was
untouched, and the refusal landed on whoever arrived second — usually the
victim.

**Fixed** by ADR-039: spending is a single atomic `SET NX`, and losing that race
raises `users.token_version`, which invalidates every token the account holds.
The teardown is committed before the refusal is raised, because an exception
would otherwise roll back the revocation that accompanies it.

### 6.10 Revoked and released rows still consumed plan capacity — fixed

Found while implementing the two above, and a real availability defect rather
than a theoretical one. `TEAM_MEMBERS` counted every membership row, so removing
a colleague on a two-seat plan would have consumed the seat permanently and made
removal a one-way door out of the plan. `WHATSAPP_NUMBERS` excluded `disabled`
but not `released`, so handing a number back would have cost a slot forever.

**Fixed** in `EntitlementService._resource_count`: the rule is "does this still
occupy something?", not "does a row exist".

### 6.11 A template sync used the platform credential — fixed

`TemplateService.sync` read a workspace's message templates from Meta with
`settings.meta_access_token`, using a `waba_id` the workspace had typed in. Two
problems, one of which ADR-037 already closes: before ownership proof the
`waba_id` was unverified, so a workspace could name a business account it had
nothing to do with and have the platform credential fetch that account's
templates.

**Fixed** on both sides: `waba_id` is now Meta's own answer from the ownership
check, and the sync resolves the credential the same way a send does — a
workspace with its own token reads with it. The sync is also restricted to live
claims, so a released number cannot be synced.

### 6.12 The API answered before the write was durable — fixed

Found by driving the container over HTTP, and not findable any other way: the
entire test suite runs through httpx's in-process ASGI transport, which awaits
the whole application call — dependency teardown included — before handing back
a response object. There is no ordering to observe there.

The session committed in a `yield` dependency's teardown, which runs *after* the
response has reached the client. With a commit costing a network round trip and
an fsync that gap measured **25–75 ms** against a containerised PostgreSQL, and
during it a token minted by `POST /auth/register` was refused by `GET /auth/me`
— the user row was not yet visible. Reproduced three times in a row, and the
mechanism confirmed separately by giving a teardown a 50 ms delay and watching
it finish 64 ms after the client had the response.

The timing was the symptom. The defect was that a `201 Created` was sent before
the write was durable, so a commit failing afterwards would leave the caller
holding a success for something that never happened, with nothing in the
response to say so.

**Fixed** with `app/api/route.py`: `CommittingRoute` commits the request's
session inside the handler chain, before the response is emitted, and every
router declares it. Rollback stays with the session context manager, where it
belongs — a handler that raised is in no position to decide anything.

The regression test runs a **real socket** (`test_commit_boundary.py`), because
that is the only way to see the property at all. Its control is checked: with
the commit disabled, both assertions fail with exactly the message they were
written for.

## 7. Known gaps, not fixed here

Recorded rather than silently carried.

- ~~No password reset~~ — **shipped** with ADR-042, once the repository could
  send email. A password *change* remains beside it for somebody already signed
  in. See [SECURITY.md](SECURITY.md).
- **Email verification is not an authorization input, and that is deliberate**
  (ADR-043). `users.email_verified_at` is written by one service and read by no
  dependency: no route, role, membership or entitlement consults it. An
  unverified account reaches every route a verified one does, and a test in
  `tests/integration/test_email_verification_endpoints.py` pins that so nobody
  "fixes" it into a lockout of every account created before the column existed.
  If a product rule ever needs a verified address, it belongs in this matrix as
  an explicit column rather than as a scattered check.
- **Revocation is per-user, not per-session.** Signing one device out while
  leaving another alone needs a session table; ADR-036 records why one was not
  built. Note that this is *session* revocation — workspace membership
  revocation is per-membership and does not touch the token estate (ADR-038).
- **`POST /auth/logout` is unauthenticated and unlimited.** Revoking a token you
  hold is legitimate, but anyone who obtains a victim's refresh token can also
  revoke it. Since ADR-039 the consequence is larger, and in the defender's
  favour: a logout followed by a refresh with the same token is a replay, and
  tears the estate down.
- **Registration discloses whether an address or slug is taken** (W-12).
- **The limiter fails open on a Redis error** (W-14) — deliberate, and a real
  residual risk for the authentication policy specifically.
- **Numbers claimed before ADR-037 have no proof.** `ownership_verified_at` is
  null on those rows and they are not refused at send time; breaking every
  existing deployment's traffic to close a claim-time hole would be the worse
  outage. The null is the list an operator re-verifies from, which is why it was
  not back-dated.
- **Ownership is proven once, at claim time.** A number that moves at Meta after
  the fact is not noticed. Re-verification on a schedule is the obvious next
  step and is not built.
- **DNS rebinding is not defeated** by `validate_outbound_url`: a name that
  resolves to a public address at check time and a private one when the socket
  opens would pass. Closing it needs the connection pinned to the checked
  address. Recorded in `app/core/net.py`.
- **A released number cannot be reclaimed by its previous holder without
  re-proving control.** That is the intended semantic, not an oversight, but it
  means an accidental release costs a round trip through Meta.
